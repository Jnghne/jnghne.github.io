파티 목록 조회 API 슬로우쿼리 개선

에이치소사이어티 · 소셜 매칭 플랫폼 · MySQL 8.0(InnoDB) · Spring Boot · MyBatis

요약

앱 메인에서 매번 호출되는 파티 목록 조회가 1초 넘게 걸렸습니다. 인덱스는 있는데도 풀스캔이 돌던 쿼리였고, 결과를 그대로 유지하면서 DB 순수 쿼리 기준 1,194ms에서 74ms로 줄였습니다. 운영 API 응답은 약 1,163ms에서 92ms로, 읽기 DB CPU 일평균은 3.52%에서 1.57%로 내려갔습니다. DDL이나 인덱스 추가, 자바 코드 변경 없이 MyBatis 매퍼만 고쳤습니다.

상황

POST /party/partyList는 앱 '모든 파티' 탭을 열 때마다 실행되는 쿼리라 체감이 큰 경로였습니다. 슬로우 쿼리 알림이 떠서 확인해 보니, 정작 필터 조건에 쓰는 REG_DATE 컬럼에는 인덱스(PARTY_REG_DATE_IDX)가 걸려 있었습니다. 인덱스가 있는데 왜 안 타는지가 출발점이었습니다.

원인

EXPLAIN ANALYZE를 떠 보니 PARTY 테이블 약 142만 행을 통째로 읽고 있었고(type=ALL, key=null), 전체 1,194ms 중 1,036ms가 이 스캔에서 나왔습니다.

AND A.REG_DATE BETWEEN DATE_ADD(NOW(), INTERVAL -(8 + EXTENSION_DAYS) DAY) AND NOW()

문제는 BETWEEN의 하한이 상수가 아니라 같은 행의 EXTENSION_DAYS 값에 걸려 있다는 점이었습니다. 경계값이 행마다 달라지니 B-Tree로 구간을 좁힐 수가 없고, 옵티마이저는 모든 행을 읽어 하나씩 경계를 계산할 수밖에 없습니다. 흔히 말하는 non-sargable 조건입니다. 이 조건 자체는 예전부터 있었는데, 테이블이 142만 행까지 커지면서 비로소 문제로 드러난 경우였습니다.

해결

기존 조건은 비즈니스 규칙(노출 기간이 파티마다 다름)이라 손대기 어려웠습니다. 그래서 조건은 그대로 두고, 인덱스를 태울 수 있는 더 느슨한 하한을 한 줄 덧붙였습니다.

-- 인덱스 탐색용 하한 (기존 조건은 그대로 유지)
AND A.REG_DATE >= DATE_ADD(NOW(), INTERVAL -(8 + (SELECT MAX(EXTENSION_DAYS) FROM PARTY)) DAY)

전체 EXTENSION_DAYS의 최댓값은 어떤 행의 값보다도 크거나 같으니, 이 하한은 실제 하한보다 항상 느슨합니다. 그래서 새로 걸러지는 행이 없어 결과가 바뀌지 않습니다. 정확한 노출 판정은 기존 BETWEEN이 그대로 하고, 추가한 줄은 옵티마이저에게 "이 날짜 이후만 인덱스로 읽어라"는 힌트 역할만 합니다. MAX(EXTENSION_DAYS) 서브쿼리는 바깥 행과 무관해서 인덱스 MIN/MAX 최적화로 쿼리당 한 번만 계산되고(EXPLAIN에서 Select tables optimized away, <cache>로 확인), 사실상 비용이 없습니다.

경계값을 무엇으로 잡을지는 대안을 몇 개 놓고 비교했습니다.

안 방식 DDL 정책값 변경 판단

짚고 넘어간 부분

"상위집합이라 결과가 안 바뀐다"는 논리를 다시 검토하다가 구멍을 하나 찾았습니다. DATE_ADD는 DATETIME 범위를 벗어나면 NULL을 반환하는데, 만약 설정에 비정상적으로 큰 값이 들어오면 하한이 NULL이 되어 결과가 통째로 사라질 수 있었습니다(dev에서 재현했습니다). 실무에서 EXTENSION_DAYS는 0~7 사이로만 쓰이고 오버플로가 나려면 약 74만 일이 필요하니 현실적으로는 일어나지 않지만, 값이 들어오는 쪽을 막는 게 낫다고 봤습니다. 그래서 설정을 편집하는 어드민 입력 단계에 상한 30일 가드를 따로 넣어 MAX ≤ 30을 보장했습니다. 읽기 쿼리는 정확성만 챙기고, 성능 보호는 쓰기 쪽에서 하도록 역할을 나눈 셈입니다.

검증

결과가 같은지와 빨라졌는지를 나눠서 봤습니다.

결과 동일성은 수정 전 서버와 수정 후 서버에 같은 요청을 보내 응답을 비교했습니다. 정렬·페이징·필터를 조합한 12개 시나리오를 전부 돌렸고, 호출 시각(currentTime)만 빼면 partySeq, 정렬 순서, memberCount, title까지 실제 값이 12개 모두 일치했습니다. 필터로 실제로 걸러지는 케이스(키워드 15건, 타입 20건, 전체 조합 1건)도 같아서 빈 응답끼리 우연히 맞은 게 아님을 확인했습니다.

속도는 DB EXPLAIN ANALYZE로 1,194ms → 74ms(약 16배)였고, 읽는 행도 약 142만 행에서 5,880행으로 줄었습니다(Table scan → PARTY_REG_DATE_IDX Index range scan, 옵티마이저 cost 163,302 → 2,961). 운영 서버에서는 12개 시나리오를 각각 웜업 1회 뒤 3번씩 재서 중앙값을 냈고, 그 평균이 약 1,163ms → 92ms였습니다.

DB 부하도 확인했습니다. 배포 전 69일과 배포 후 50일(배포 주 제외)을 CloudWatch로 비교하면 읽기 DB CPU 일평균은 3.52% → 1.57%, 일 최대값 평균은 9.28% → 5.03%로 내려갔습니다. 같은 기간 SELECT/초(378 → 368)와 하루 API 요청 수(약 572만 → 558만 건)는 거의 그대로여서, 트래픽이 줄어서 생긴 변화가 아니라는 것도 함께 봤습니다. 배포 후 30일 동안 Prometheus로 실사용 트래픽까지 지켜봤는데, 배포일을 기점으로 평균 응답이 약 1,120ms에서 64ms로 떨어진 뒤 다시 오르지 않았습니다.

돌아보며

인덱스가 걸려 있다고 다 타는 게 아니라는 걸 실제 사례로 확인했습니다. 컬럼을 함수로 감싸거나 비교 경계에 다른 컬럼을 넣으면 인덱스가 죽습니다. 그리고 못 바꾸는 조건이라도, 그걸 포함하는 더 느슨한 조건을 덧대면 결과를 유지하면서 인덱스를 유도할 수 있다는 것도 남는 경험이었습니다. 한 가지 더, 이 쿼리는 피크가 2.7 RPS로 트래픽 자체는 낮았는데도 문제가 됐습니다. 1초짜리 쿼리가 핫패스에서 공용 HikariCP 커넥션을 오래 붙잡고 있어서 다른 API 지연까지 끌고 갔기 때문입니다. 병목이 처리량이 아니라 커넥션 점유 시간일 수 있다는 걸 이때 체감했습니다.

운영 배치 서버 OS 메모리 상승 진단

에이치소사이어티 · Java · Spring Boot · ParallelGC · Prometheus / Grafana / CloudWatch · pmap · GC 로그 · NMT

요약

배치 서버(물리 7.6GiB)의 OS 메모리가 몇 달에 걸쳐 80%까지 차오르면 수동 재기동으로 넘기고 있었습니다. 계측을 이원화해 대조하고 pmap·GC 로그·수동 Full GC 실험으로 파고든 결과, 메모리 누수가 아니라 7.6GiB 서버에 heap을 6GiB로 과하게 고정해서 생기는 구조적 현상이었습니다. heap을 4.5GiB로 줄이는 단일 변경으로 정리했고, 운영과 동일 사양 서버에서 검증까지 통과했습니다(운영 적용 대기).

상황

sp-prod-batch-svr1(물리 7.6GiB, -Xms6144M -Xmx6144M, ParallelGC)의 OS 메모리가 시간이 지나며 선형으로 늘어, 몇 달마다 80% 알람에 닿으면 사람이 재기동해 왔습니다. JVM 힙 모니터링만 보면 아무 이상이 없었습니다.

진단

한 번에 답을 맞힌 게 아니라 가설을 세우고 데이터로 틀렸다는 걸 확인하며 좁혀 갔습니다.

CloudWatch 장기 그래프가 톱니형으로 시간에 비례해 우상향해서 부하 스파이크가 아닌 누적성 문제로 봤고, 재기동하면 리셋되니 주체는 이 배치 JVM이었습니다. 다음으로 Prometheus(JVM 내부)와 CloudWatch(OS 물리)를 겹쳐 보니 JVM 지표는 평평한데 OS만 올라 한때 native 누수를 의심했습니다. 여기서 committed(예약)·RSS(실제 물리 점유)·used(살아 있는 객체)를 구분했는데, Prometheus는 used만 보여줘 "used는 멀쩡한데 OS만 오른다"는 착시가 생겼습니다. 실제 물리 점유는 pmap으로 떠야 보였고, VmRSS를 heap/native로 쪼개니 glibc arena 파편화는 아니었고 늘어나는 건 heap RSS였습니다.

결정타는 수동 Full GC 실험이었습니다. Full GC를 강제로 돌리자 Old 영역이 2.1GiB에서 90MiB로 회수됐는데 RSS는 그대로였습니다. 쌓여 있던 게 살아있는 객체가 아니라 회수 가능한 쓰레기였고, ParallelGC가 한 번 touch한 페이지를 OS에 돌려주지 않는다는 걸 직접 확인한 것입니다.

원인 (확정)

heap leak이 아니라 과대 고정 heap의 구조적 결과였습니다.

heap 6GiB 고정(Xms=Xmx) + ParallelGC
→ Full GC가 거의 안 돌아 Old에 죽은 객체가 계속 쌓임 (~100MB/일)
→ 그때마다 새 heap 페이지가 touch되어 RSS 증가
→ GC로 객체는 회수돼도 touch된 페이지는 OS에 반환 안 됨
→ 서버 메모리가 계단식으로 누적

게다가 정상 상한 자체가 heap 6.0 + native 0.6 + 기타 프로세스 0.45 ≈ 7.05GiB로 **서버의 93%**였습니다. 즉 80% 알람은 설계상 필연이었고, 재기동은 시계를 되돌리는 임시 대응일 뿐이었습니다.

근거 (GC 로그 4.7일 실측)

순수 live 객체는 78~91 MiB, GC 직후 used 최대도 486 MiB로 대부분이 회수 가능한 Old 누적분이었습니다. 무거운 배치 구간(매일 점심 매칭·블랙 매칭, 주말 푸시)도 할당만 많고 유지는 안 해서 GC당 승격이 수십 MB에 그쳤습니다 — 메모리를 오래 쥐는 배치는 없다는 걸 실측으로 확정했습니다.

해결 (확정)

heap을 6G에서 4.5G(-Xms4608M -Xmx4608M)로 줄이는 단일 변경, GC는 ParallelGC 유지로 정했습니다. 함께 GC 로그·NMT·HeapDumpOnOutOfMemoryError를 켜서 이후 진단 여지를 확보했습니다.

4.5G는 80% 알람 밑으로 확실히 들어가는 것 중 가장 큰 heap입니다. 서버 상한이 (4.5 + native 0.6 + 기타 0.45)/7.6 ≈ **73%**로, 관측된 live 상한(0.49G)의 약 9배 여유입니다. 5.0G는 상한이 정확히 80% 알람선에 걸려 제외했습니다. GC를 바꾸지 않은 이유는 원인이 GC 종류가 아니라 heap 크기라, 변경 변수를 하나로 유지해 효과를 명확히 검증하려 했고 배치 서버엔 처리량 위주의 ParallelGC가 적합하기 때문입니다.

검증

운영과 동일 사양 서버에서 heap 4.5G로, 메모리가 천장까지 찬 상태(AlwaysPreTouch)를 미리 만들어두고 가장 무거운 배치 3종(점심 매칭·블랙 매칭·주말 푸시)을 운영처럼 겹쳐 동시 실행했습니다. 전부 정상 완주, OOM 0, GC 직후 최대 153M(기준 1G의 15%), heap RSS 천장 고정, native는 워밍업 후 0.40G에서 정체, 서버 70% 유지 — 운영 적용에 문제없음으로 판정했습니다(2026-08-07). 현재 운영 적용 대기입니다.

적용 후 기대 (오해 방지)

이건 "메모리가 안 오르게" 만드는 게 아닙니다. 고정 heap 특성상 CloudWatch는 여전히 한 달쯤 우상향하다 약 73%에서 멈춥니다. 성공 기준은 "안 오르는 것"이 아니라 73% 근처에서 멈추고 80%를 넘지 않는 것이고, 그러면 80% 알람이 다시 진짜 이상(native 증가·미지의 대형 배치)을 알리는 신호로 살아납니다.

돌아보며

메모리가 는다고 다 누수는 아니라는 걸 확인한 사례입니다. GC가 정상이어도 RSS 최고치와 페이지 미반환 때문에 OS 메모리는 오를 수 있고, committed·RSS·used를 구분 못 하면 Prometheus만 보고 정상이라 오판하기 쉽습니다. native 같은 그럴듯한 가설을 pmap·GC 로그로 반증했고, 특히 수동 Full GC로 "Old를 비워도 RSS는 안 준다"를 직접 보인 게 원인 확정의 결정타였습니다. 해결도 "누수를 잡는다"가 아니라 "서버에 맞게 heap을 적정화하고 성공 기준까지 재정의한다"로 접근한 게 핵심이었습니다.

분산 환경 댓글 닉네임 동시성 결함 개선

에이치소사이어티 · Java 21 · Spring Boot · MyBatis · 다중 EC2 · JUnit5

요약

여러 EC2에 요청이 분산되는 환경에서, 같은 회원이 같은 글에 거의 동시에 댓글을 달면 서로 다른 익명 닉네임이 두 개 생기는 문제가 있었습니다. 분산락이나 새 테이블, Redis 없이 닉네임 생성을 결정론적(멱등) 방식으로 바꿔서 해결했고, 렌즈와 커뮤니티 두 도메인에 같은 방식을 적용했습니다.

상황

익명 닉네임을 쓰는 댓글/답글에서, 같은 회원이 같은 원글에 첫 댓글을 거의 동시에 두 번 달면 닉네임이 두 개 만들어졌습니다. 요청이 서로 다른 인스턴스로 갈 때 특히 잘 재현됐고, 렌즈 댓글과 커뮤니티 익명 라운지 댓글 양쪽에 똑같이 있었습니다.

원인

닉네임 생성이 "조회해서 없으면 만든다"는 비원자 패턴이었습니다. 두 요청이 조회에서 모두 null을 읽고 각자 new Random()으로 만들면, 같은 원글·같은 작성자인데 닉네임이 갈립니다(작성자당 하나여야 한다는 규칙이 깨집니다). 두 도메인 모두 (원글, 작성자)로 조회하는 구조가 같아서 결함도 같았습니다.

대안 비교

방안 원자성 추가 비용 채택

기존 댓글 테이블에 (원글, 작성자) UNIQUE 제약을 거는 방법도 검토했지만, 한 사람이 같은 글에 댓글을 여러 개 달 수 있어야 해서 적용할 수 없었습니다. DB로 보장하려면 닉네임만 따로 담는 매핑 테이블이 필요했고, 그게 위 표의 두 번째 안입니다.

닉네임은 익명 표시용이라 서로 다른 유저끼리 우연히 겹치는 건 원래 허용되는 성격입니다. 그래서 "절대 안 겹치게"가 아니라 "동시에 만들어도 같은 값이 나오게"만 하면 됐고, 그 조건을 비용 없이 만족하는 게 결정론 방식이었습니다.

해결

닉네임 생성을 (orgNo, recCd)를 시드로 쓰는 멱등 함수로 바꿨습니다. 입력이 같으면 결과가 항상 같으니, 인스턴스끼리 통신하지 않아도 같은 닉네임이 나와서 "충돌"이라는 상황 자체가 생기지 않습니다.

// (orgNo, recCd)를 시드로 고정 → 같은 키는 항상 같은 닉네임
public String getStableNickName(String gender, long orgNo, String recCd) {
    return composeNickName(gender, new Random(31L * orgNo + recCd.hashCode()));
}

String.hashCode()와 Random(seed)는 JVM 스펙에 고정돼 있어서 어느 인스턴스, 어느 시점에 계산해도 같은 값이 나옵니다. 여기에 앱 버튼 디바운스(0.8초)를 1차로 두고 서버 결정론 생성을 근본 처리로 두는 식으로 계층을 나눴습니다.

작업하다 닉네임 명사 배열이 형용사 배열 길이만큼만 채워져서 뒤쪽 명사 73개(여 32, 남 24, 기타 17)가 아예 안 뽑히던 버그도 발견해서 고쳤습니다. 렌즈·커뮤니티 공통 함수라 양쪽에 반영됐습니다. 렌즈에서 고친 뒤 커뮤니티 댓글에도 같은 구조가 있는 걸 확인하고 공통 메서드로 묶어 재사용했습니다.

검증

getStableNickName은 외부 의존이 없는 순수 함수라 mock 없이 실제로 테스트했습니다. 성별별로 같은 키를 50번 호출해 결과가 하나로 나오는지(멱등성 3종), recCd·orgNo를 각각 20종 넣어 결과가 충분히 흩어지는지(키 반영 2종)를 확인했고, 별도 프로세스에서 같은 시드로 돌렸을 때 난수 시퀀스가 똑같이 나오는 것도 봤습니다.

돌아보며

동시성 문제라고 꼭 락이 답은 아니라는 걸 배운 사례입니다. 지켜야 할 규칙을 "생성 결과가 항상 같다"로 바꾸면 락 없이도 race가 의미가 없어집니다. 닉네임이 익명 표시용이라 우연한 중복은 원래 괜찮다는 요구사항의 성격을 정확히 본 게 비용 없는 해법으로 이어졌고, 한 곳을 고친 뒤 다른 도메인에서 같은 결함을 찾아 함께 묶은 것도 재발 방지에 도움이 됐습니다.

같은 글 안에서 랜덤 닉네임이 겹치는 문제 개선

에이치소사이어티 · Java 21 · Spring Boot · MyBatis · MySQL(InnoDB, 약 9,600만 행)

요약

같은 게시글에서 서로 다른 두 사람이 우연히 같은 랜덤 닉네임을 받아 누가 누군지 헷갈리는 문제가 있었습니다(30일 평균 183건). UI나 DDL, 인프라 없이 "이미 쓰인 닉네임을 빼고 결정론적으로 고르는" 방식으로 바꿔, 반영 후 9월까지 2건으로 줄였습니다(3번과 같은 PR #48에서 함께 처리했습니다).

상황

익명 라운지와 렌즈에서 닉네임은 형용사 + 명사(예: 귀여운다람쥐)로 랜덤 발급됩니다. 한 스레드 안에서는 작성자마다 하나로 고정되고 서로 다른 작성자는 다르게 보여야 대화가 되는데, 실제로는 다른 두 사람이 같은 닉네임을 받는 일이 생겼습니다. 3번의 "같은 사람이 여러 닉네임을 받는" 동시성 문제와는 별개로, 다른 사람끼리 우연히 겹치는 경우입니다.

원인

조합 풀이 유한한데(여 5,073, 남 4,756, 기타 2,478) 각자 독립적으로 뽑고, 다른 사람이 이미 쓴 걸 확인하지 않았습니다. 참여자가 많아지면 생일 문제로 충돌 확률이 빠르게 올라서, 여성 풀 기준 75명이면 42.1%까지 갑니다. 유일성은 뽑는 시점에 "남들이 뭘 썼는지"를 알아야 보장되는데, 배열을 늘리거나 시드를 바꾸는 무상태 방식으로는 이 확률 하한을 못 넘는 걸 실측으로 확인했습니다.

개선 전 기준치(원글 생성일 기준 2026년 4~6월)는 이랬습니다.

전체 원글 충돌 원글 원글당 충돌률
커뮤니티 185,723 490 약 0.264%
렌즈 1,803 25 약 1.39%

비율은 낮아도 매달 180건 넘게 실제 불편이 생기고 있어서 고치기로 했습니다.

대안 비교

방안 유일성 DDL/인프라 형태 메모

마지막까지 H와 D를 놓고 고민했습니다. D를 안 쓴 이유는, 얻는 게 "연 1건 미만을 0건으로" 정도인데 그 대가로 DDL, 수천만 행 마이그레이션, 본문과 매핑 테이블 이중 관리를 떠안기 때문입니다. 게다가 마이그레이션을 안 하면 과거 글에서는 D가 오히려 H보다 못합니다(H는 본문을 조회하니 과거 닉네임도 바로 보입니다). 나중에 닉네임 이력이나 관리자 조회 때문에 매핑 테이블이 정말 필요해지면 그때 H 위에 D를 얹으면 됩니다.

해결 (방안 H)

발급하기 전에 그 글에서 이미 쓰인 닉네임을 조회해 후보에서 빼고, 고정된 전체 풀에서 (orgNo, recCd) 시드로 시작 위치를 정한 다음 순환하며 처음 비어 있는 닉네임을 돌려줍니다.

public String getAvailableNickName(String gender, long orgNo, String recCd, Set<String> used) {
    List<String> pool = NickNamePool.pool(gender);   // static 캐싱된 전체 조합 (고정)
    int size = pool.size();
    long seed = 31L * orgNo + recCd.hashCode();
    int start = Math.floorMod(seed, size);           // 시작 위치는 used와 무관하게 고정
    for (int i = 0; i < size; i++) {
        String candidate = pool.get((start + i) % size);
        if (!used.contains(candidate)) return candidate;  // 처음 비어 있는 후보 반환
    }
    return getStableNickName(gender, orgNo, recCd);  // 풀이 다 찼을 때의 fallback
}

처음엔 used를 뺀 리스트를 만들어 avail.get(seed % avail.size())로 뽑았는데, 코드 리뷰에서 문제가 잡혔습니다. 분모가 avail.size()라 상관없는 다른 사람이 닉네임 하나만 더 써도 크기가 바뀌어, 같은 사람이 재요청 때 다른 닉네임을 받을 수 있었습니다. 이러면 3번에서 고친 "같은 사람 여러 닉네임" 문제가 다시 생깁니다. 그래서 전체 풀에서 시작점을 잡고 순환하는 방식으로 바꿔 분모를 고정했고, 요청마다 리스트를 새로 만들던 것(약 20KB)도 없앴습니다.

검증

조회 비용부터 봤습니다. ORG_NO 인덱스가 이미 있어서 커뮤니티는 9,600만 행에서도 index_merge로 rows=4 수준이고 풀스캔이 없습니다. 조회는 그 사람이 그 글에 처음 댓글 쓸 때만 일어나서 초당 0.2회 정도입니다.

남는 동시성 리스크도 계산해 봤습니다. "조회~INSERT 사이(약 50ms)에 신규 유저 둘이 같은 글에 동시 진입"하고 동시에 "남은 풀 약 5,000개에서 하필 같은 걸 고르는(1/5,000)" 경우가 겹쳐야 해서, 연 0.3건 미만으로 계산했습니다. 단위 테스트는 제외·대체·무관한 닉 추가 시 유지·멱등성·풀 소진까지 10종을 뒀습니다.

반영 후 모니터링 집계로 확인해 보니, 같은 글에서 서로 다른 회원에게 같은 닉네임이 발급된 건은 30일 평균 183건에서 7월 반영 이후 9월까지 2건으로 줄었습니다. 2건은 계산보다 많았는데, 원인은 이 방식의 한계였습니다. 두 사용자의 요청이 완전히 겹치면 둘 다 같은 "사용 중 닉네임 목록"을 보고 후보를 고르고, 이때 글·사용자 조합으로 정해지는 후보가 우연히 같으면(남성 풀 4,756개 기준 1/4,756) 결정론적으로 같은 닉네임이 나옵니다. 남은 경합 구간이 실제로 관측된 셈이라, 더 줄이려면 그때 D 방식(UNIQUE 매핑 테이블)을 얹는 게 다음 단계입니다.

돌아보며

문제를 생일 문제로 놓고 확률을 계산한 덕에, "그냥 단어를 늘리자"는 직관적인 안이 왜 근본 해결이 아닌지(병목이 조합 수가 아니라 남의 상태를 안 보는 데 있다는 점)를 설명할 수 있었습니다. 그리고 이론상 완전한 D가 항상 최선은 아니고, 마이그레이션·이중 관리까지 총비용으로 보면 H가 나았습니다. 이 판단을 수치로 정리해 둔 게 리뷰에서 설득에 도움이 됐고, 리뷰가 "조건부 결정론"이라는 미묘한 결함을 잡아 준 것도 좋았습니다.

그룹웨어 게시판 통합 조회 슬로우쿼리 튜닝

엠케이원 · Amaranth10 그룹웨어 · MySQL · MyBatis · 2023

요약

모든 게시판의 글을 모아 보여주는 "최근 게시글" 화면이 특정 고객사에서 약 7초 걸렸습니다. 인덱스를 추가하지 않고 쿼리 구조만 다시 짜서 3초 미만으로 줄였습니다.

상황

"최근 게시글"은 일반 게시판과 달리 전체 게시판의 글을 등록순으로 보여주는 게시판입니다. 전임자에게서 언젠가 튜닝이 필요할 API라고 인계받았지만, 직접 재 보니 2~3초 수준이라 우선순위를 미뤄 두었습니다. 그러다 인프라팀에서 한 고객사에서 이 목록이 유독 느리다는 연락이 왔고, 현장에서 재 보니 약 7초가 걸렸습니다.

원인

이 쿼리는 최근 게시글만이 아니라 여러 API가 함께 쓰는 게시판 메인 쿼리였습니다. 여러 개발자의 수정이 쌓이면서 길고 복잡해졌고, 필요 없는 조인과 이미 조인한 데이터를 다시 읽는 서브쿼리가 남아 있었습니다. 데이터가 많은 고객사에서 이 비효율이 한꺼번에 드러난 경우였습니다.

해결

인덱스를 더하기 전에 쿼리 구조만으로 충분히 줄일 수 있다고 보고, 쿼리를 분석해 아래 순서로 정리했습니다.

  • LEFT JOIN → INNER JOIN, 쿼리 분리: 게시판과 게시글은 구조상 항상 매칭되는데 LEFT JOIN으로 묶여 있었습니다. 다만 일부 게시판 유형은 트리 구조 정보가 없어 LEFT JOIN이 꼭 필요했습니다. 그래서 그 유형만 LEFT JOIN을 유지하고 나머지는 INNER JOIN을 쓰도록 쿼리를 나눴고, 공통 SELECT 절은 MyBatis <sql>/<include>로 묶어 중복을 막았습니다. 이 단계에서만 3초 이상 줄었습니다.
  • 중복 서브쿼리 제거: 같은 사원 테이블을 user_id로 두 번 읽던 스칼라 서브쿼리를 LEFT JOIN 한 번으로 바꿨습니다.
  • 동적 SQL: 관리자 목록처럼 권한 확인이 필요 없는 경우에는 if/choose로 권한 조인과 쓰지 않는 컬럼을 건너뛰게 했습니다.

결과적으로 응답 시간은 약 7초에서 3초 미만으로 줄었습니다.

돌아보며

처음 2~3초였을 때 "아직 괜찮다"고 미룬 쿼리가 데이터가 많은 고객사에서 7초가 됐습니다. 여러 API가 공유하는 쿼리일수록 수정이 쌓이며 조금씩 무거워지기 쉽고, 데이터가 커지면 그게 한 번에 터진다는 걸 배웠습니다. 또 느린 쿼리라고 바로 인덱스부터 찾기보다, 쿼리가 정말 필요한 데이터만 읽고 있는지부터 보는 게 먼저라는 것도 남은 경험입니다.

대용량 엑셀 마이그레이션 (POI 전체 로딩 → SAX 스트리밍)

엠케이원 · Java · Spring Boot · Apache POI · 2023

요약

마이그레이션 자동화 애플리케이션에서 대용량 엑셀을 읽어 DB에 저장하는 API를 맡았습니다. 엑셀을 통째로 메모리에 올리던 방식이 5만 건을 넘기면 느려지고 OOM이 나서, SAX 기반 스트리밍 파싱으로 다시 구현했고 15만 행을 13초에 처리하게 됐습니다.

상황

처음에는 Apache POI의 XSSFWorkbook으로 구현했습니다. 코드가 간단하다는 장점이 있었지만, 데이터가 5만 건 정도를 넘어가면 속도가 크게 떨어지고 OOM이 발생했습니다.

원인

XSSFWorkbook은 워크북 전체를 객체 트리로 메모리에 올립니다. 셀 하나하나가 자바 객체가 되기 때문에, 행이 늘어날수록 힙 사용량이 함께 커집니다.

해결

엑셀을 한 번에 올리지 않고 행 단위로 읽는 POI의 이벤트 기반 방식으로 바꿨습니다.

  • OPCPackage로 파일을 열고 XSSFReader에서 시트 데이터와 StylesTable, ReadOnlySharedStringsTable을 가져옵니다.
  • SAX XMLReader에 XSSFSheetXMLHandler를 연결하고, SheetContentsHandler를 구현한 핸들러에서 행을 순서대로 받아 처리합니다. 숫자가 지수 표기로 바뀌지 않도록 DataFormatter에 DecimalFormat을 지정했습니다.
  • 읽은 데이터는 템플릿 헤더 행과 필수값이 빈 행, 빈 시트를 걸러낸 뒤 헤더 기준 Map으로 바꿔 넘깁니다.
  • 처리 시간이 길어 요청을 붙잡지 않도록 전용 ThreadPoolTaskExecutor(core 5, max 20, queue 50)에서 비동기로 처리하고, 컨트롤러는 먼저 응답하게 했습니다.

결과적으로 15만 행 기준 13초에 처리하게 됐습니다.

돌아보며

스트리밍 파싱은 메모리를 적게 쓰는 대신 랜덤 접근이 안 되고 코드가 길어집니다. "순서대로 읽어서 넣는다"는 이 기능의 목적에는 그 제약이 문제가 되지 않아 잘 맞았습니다. 다만 지금 구조는 파싱만 스트리밍이고 읽은 행은 리스트에 모아 두기 때문에, 파일이 더 커지면 일정 행 단위로 끊어서 바로 저장하는 방식이 다음 개선 지점이라고 봅니다.
