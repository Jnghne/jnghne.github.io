파티 목록 조회 API 슬로우쿼리 개선

에이치소사이어티 · 스카이피플 · MySQL 8.0 · Spring Boot · MyBatis

앱의 '모든 파티' 탭을 열 때마다 호출되는 목록 조회가 1.2초씩 걸렸습니다. 날짜 인덱스가 있는데도 142만 행을 전부 읽고 있었고, 조건 한 줄을 추가해 74ms로 줄였습니다. 조회 결과는 그대로이고, DDL이나 자바 코드는 바꾸지 않았습니다.

문제

슬로우 쿼리 알림을 보고 POST /party/partyList를 확인했습니다. 필터에 쓰는 REG_DATE에는 인덱스가 있었지만, EXPLAIN ANALYZE를 보면 PARTY 테이블 142만 행을 전부 읽고 있었습니다. 전체 1,194ms 중 1,036ms가 이 스캔이었습니다.

원인

AND A.REG_DATE BETWEEN DATE_ADD(NOW(), INTERVAL -(8 + EXTENSION_DAYS) DAY) AND NOW()

날짜 범위의 시작점이 같은 행의 EXTENSION_DAYS에 따라 달라집니다. 행마다 기준이 다르니 인덱스로 범위를 좁힐 수 없고, 모든 행을 읽어 하나씩 비교할 수밖에 없었습니다. 예전부터 있던 조건인데 테이블이 커지면서 문제가 됐습니다.

해결

노출 기간이 파티마다 다른 건 정책이라 기존 조건은 그대로 두고, 모든 파티를 포함하는 넉넉한 시작점을 한 줄 추가했습니다.

-- 인덱스로 범위를 먼저 좁히기 위한 조건 (기존 조건은 유지)
AND A.REG_DATE >= DATE_ADD(NOW(), INTERVAL -(8 + (SELECT MAX(EXTENSION_DAYS) FROM PARTY)) DAY)
  • 최댓값 기준이라 기존 조건보다 항상 넓습니다. 그래서 빠지는 행이 없고, 최종 판단은 기존 조건이 그대로 합니다. 서브쿼리는 쿼리당 한 번만 실행됩니다.
  • 상수(예: 13일)로 박지 않은 이유는 운영에서 연장 기간 설정을 늘리면 결과가 조용히 빠질 수 있어서입니다. 계산 컬럼에 인덱스를 거는 방법이 더 깔끔하지만 변경 범위가 커서 다음 과제로 남겼습니다.
  • 설정값이 비정상적으로 크면 DATE_ADD가 NULL을 반환해 목록이 통째로 비는 경우를 개발 서버에서 재현했습니다. 실제 값은 0~7일이지만, 어드민 입력 단계에 30일 상한을 추가했습니다.

결과

  • 수정 전후 서버에 필터·정렬·페이징 조합 12가지를 똑같이 요청해, 호출 시각을 빼면 응답이 모두 같은 것을 확인했습니다.
  • DB 실행 시간 1,194ms → 74ms, 읽는 행 142만 → 5,880 (인덱스 range scan)
  • 운영 API 응답 약 1,163ms → 92ms (12가지 조건별 중앙값의 평균)
  • 읽기 DB CPU 일평균 3.52% → 1.57% (배포 전 69일, 후 50일 비교. 같은 기간 요청 수는 거의 같음)

돌아보며

인덱스가 있으니 괜찮겠지 하고 넘겼으면 계속 몰랐을 문제였습니다. 그 뒤로는 느린 쿼리를 보면 인덱스가 있는지보다 실행계획에서 실제로 타는지부터 봅니다. 트래픽이 초당 2.7건뿐인데 다른 API까지 느려졌던 것도, 이 쿼리가 커넥션을 1초씩 잡고 있었기 때문이었습니다.

배치 서버 메모리 상승 원인 규명

에이치소사이어티 · 스카이피플 · Java · Spring Boot · ParallelGC · Prometheus · CloudWatch

배치 서버 메모리가 몇 달마다 80% 알람에 닿아 그때마다 재기동하고 있었습니다. 누수가 아니라 7.6GiB 서버에 heap을 6GiB로 크게 고정한 탓이었고, heap을 4.5GiB로 줄여 메모리 상한을 93%에서 73%로 낮췄습니다.

문제

배치 서버(7.6GiB, -Xms6144M -Xmx6144M, ParallelGC)의 OS 메모리가 계속 올라 몇 달에 한 번씩 수동으로 재기동했습니다. JVM 힙 지표만 보면 이상이 없었습니다.

원인

처음엔 누수를 의심했고, 하나씩 확인하며 좁혀 갔습니다.

  • CloudWatch에서는 메모리가 계단식으로 오르고 재기동하면 내려가서, 이 배치 JVM에 쌓이는 문제로 봤습니다.
  • Prometheus의 JVM 지표는 평평한데 OS 메모리만 올라 native 누수를 의심했습니다. 알고 보니 Prometheus는 살아 있는 객체(used)만 보여줘서 생긴 착시였고, pmap으로 실제 점유(RSS)를 나눠 보니 늘어나는 건 heap 영역이었습니다.
  • Full GC를 직접 돌리자 Old 영역은 2.1GiB에서 90MiB로 줄었는데 RSS는 그대로였습니다. ParallelGC는 한 번 사용한 heap 메모리를 OS에 돌려주지 않습니다.
  • GC 로그 4.7일치를 보면 실제로 살아 있는 객체는 78~91MiB였고, 메모리를 오래 잡고 있는 배치는 없었습니다.

정리하면 Full GC가 거의 돌지 않아 Old 영역에 쓰레기가 쌓이고, 그만큼 새 메모리를 계속 쓰다 보니 heap 6GiB까지 차오르는 구조였습니다. heap 6.0 + native 0.6 + 기타 0.45GiB면 서버의 93%라, 80% 알람은 시간 문제였습니다.

해결

heap을 4.5GiB(-Xms4608M -Xmx4608M)로 줄였습니다. 이러면 상한이 73%가 됩니다. 5GiB는 상한이 딱 80%라 제외했고, 효과를 분명히 보려고 GC 종류는 바꾸지 않았습니다. 이후 진단을 위해 GC 로그, NMT, HeapDumpOnOutOfMemoryError도 켰습니다.

결과

운영과 같은 사양 서버에서 메모리를 미리 끝까지 채운 상태로, 가장 무거운 배치 3개(점심 매칭, 블랙 매칭, 주말 푸시)를 동시에 돌렸습니다. OOM 없이 모두 끝났고 서버 메모리는 70%를 유지해, 운영에 적용했습니다. 고정 heap이라 적용 후에도 메모리는 한 달쯤 오르다 73% 근처에서 멈추는 게 정상이고, 그러면 80% 알람이 다시 진짜 이상만 알리게 됩니다.

돌아보며

native 쪽을 계속 파다가 Full GC를 직접 돌려 본 게 방향을 바꿨습니다. 그 뒤로는 메모리 그래프를 볼 때 그게 used인지 RSS인지부터 확인합니다.

동시 요청 시 댓글 닉네임 중복 생성 해결

에이치소사이어티 · 스카이피플 · Java 21 · Spring Boot · MyBatis · JUnit5

같은 회원이 같은 글에 첫 댓글을 거의 동시에 두 번 달면 익명 닉네임이 두 개 생겼습니다. 서버가 여러 대라 생긴 문제였고, 락 없이 닉네임이 글과 작성자로 항상 같게 정해지도록 바꿔 해결했습니다.

문제

렌즈 댓글과 커뮤니티 익명 라운지 댓글에서, 한 사람이 같은 글에 서로 다른 닉네임 두 개로 보이는 일이 있었습니다. 두 요청이 다른 서버로 갈 때 잘 재현됐습니다.

원인

그 글에서 쓴 닉네임을 조회하고, 없으면 새로 만드는 구조였습니다. 두 요청이 동시에 조회하면 둘 다 없다고 읽고 각자 무작위로 만들었습니다.

해결

여러 방법을 비교했습니다.

  • Redis 분산락: 이 문제 하나 때문에 Redis를 새로 들이기엔 과했습니다.
  • MySQL Named Lock: 커넥션, 트랜잭션과 묶여 관리가 까다롭습니다.
  • 댓글 테이블에 (글, 작성자) UNIQUE 제약: 한 사람이 댓글을 여러 개 달 수 있어야 해서 걸 수 없었고, 하려면 매핑 테이블을 새로 만들어야 했습니다.

필요한 건 한 사람이 한 글에서 닉네임 하나만 갖는 것이었습니다. 동시에 만들어도 항상 같은 값이 나오면 경합 자체가 문제가 되지 않아서, 닉네임을 글 번호와 작성자로 정해지게 바꿨습니다.

// 같은 (글, 작성자)면 어느 서버에서 만들어도 같은 닉네임
public String getStableNickName(String gender, long orgNo, String recCd) {
    return composeNickName(gender, new Random(31L * orgNo + recCd.hashCode()));
}

String.hashCode()와 Random(seed)는 JVM 스펙으로 정해져 있어 서버가 달라도 결과가 같습니다. 앱 쪽 버튼 연타 방지(0.8초)도 함께 두었습니다. 렌즈를 고친 뒤 커뮤니티 댓글에도 같은 구조가 있어 공통 메서드로 묶었고, 작업 중 명사 배열이 형용사 개수만큼만 채워져 뒤쪽 명사 73개가 한 번도 뽑히지 않던 버그도 함께 고쳤습니다.

결과

외부 의존이 없는 함수라 mock 없이 테스트했습니다. 같은 키로 50번 호출해 항상 같은 값이 나오는지, 키를 20가지로 바꿨을 때 고르게 흩어지는지, 다른 프로세스에서도 같은 값이 나오는지 확인했습니다.

같은 글 안 닉네임 중복 발급 개선

에이치소사이어티 · 스카이피플 · Java 21 · Spring Boot · MyBatis · MySQL

같은 글에서 서로 다른 두 사람이 같은 랜덤 닉네임을 받는 일이 30일 평균 183건 있었습니다. 그 글에서 이미 쓰인 닉네임을 빼고 고르도록 바꿔, 반영 후 9월까지 2건으로 줄였습니다. 3번과 같은 PR에서 처리했습니다.

문제

익명 닉네임은 형용사와 명사를 조합해 만듭니다(예: 귀여운다람쥐). 같은 글에서 다른 두 사람이 같은 이름이면 누가 누군지 구분이 안 됩니다. 개선 전 3개월(4~6월) 기준으로 커뮤니티 원글 185,723개 중 490개(0.26%), 렌즈 1,803개 중 25개(1.39%)에서 이런 충돌이 있었습니다.

원인

만들 수 있는 조합은 성별에 따라 2,478~5,073개인데, 다른 사람이 쓴 이름을 확인하지 않고 무작위로 골랐습니다. 참여자가 늘면 겹칠 확률이 빠르게 올라가서 (생일 문제), 여성 기준 75명이 참여하면 42%가 됩니다. 단어를 늘리는 것만으로는 해결되지 않는 구조였습니다.

해결

  • 단어 늘리기: 댓글이 많은 글에서는 여전히 겹칩니다.
  • 숫자나 이모지 붙이기: 닉네임 모양이 바뀝니다.
  • 매핑 테이블 + UNIQUE: 가장 확실하지만 테이블 추가, 수천만 행 마이그레이션, 본문과 이중 관리가 필요합니다.
  • 이미 쓰인 닉네임을 빼고 고르기: DDL 없이 대부분 해결됩니다.

마지막 방법을 택했습니다. 매핑 테이블은 남은 몇 건을 0으로 만드는 데 비해 비용이 커서, 정말 필요해지면 그 위에 더하기로 했습니다.

public String getAvailableNickName(String gender, long orgNo, String recCd, Set<String> used) {
    List<String> pool = NickNamePool.pool(gender);   // 전체 조합 (고정)
    int size = pool.size();
    int start = Math.floorMod(31L * orgNo + recCd.hashCode(), size);
    for (int i = 0; i < size; i++) {
        String candidate = pool.get((start + i) % size);
        if (!used.contains(candidate)) return candidate;  // 안 쓰인 첫 후보
    }
    return getStableNickName(gender, orgNo, recCd);  // 풀을 다 쓴 경우
}

처음에는 남은 후보 목록의 크기로 나눠서 골랐는데, 코드 리뷰에서 문제가 나왔습니다. 다른 사람이 닉네임을 하나만 더 써도 목록 크기가 바뀌어, 같은 사람이 다시 요청할 때 다른 닉네임을 받을 수 있었습니다. 3번 문제가 다시 생기는 셈이라, 전체 목록에서 시작 위치를 고정하고 순서대로 찾는 방식으로 바꿨습니다.

결과

  • 사용 중 닉네임 조회는 기존 인덱스로 처리돼, 9,600만 행 테이블에서도 몇 행만 읽습니다.
  • 단위 테스트 10개로 제외, 재요청 시 유지, 풀 소진 케이스를 확인했습니다.
  • 중복 발급 30일 평균 183건 → 7월 반영 후 9월까지 2건

남은 2건은 두 사람의 요청이 완전히 겹쳐 같은 사용 중 목록을 보고 고를 때, 시작 위치까지 우연히 같은 경우(약 1/4,756)였습니다. 이것까지 막으려면 그때 매핑 테이블을 더하면 됩니다.

그룹웨어 게시판 조회 쿼리 튜닝

엠케이원 · Amaranth10 그룹웨어 · MySQL · MyBatis · 2023

모든 게시판의 글을 모아 보여주는 최근 게시글 화면이 한 고객사에서 약 7초 걸렸습니다. 인덱스를 추가하지 않고 쿼리 구조만 정리해 3초 미만으로 줄였습니다.

문제

전임자에게 언젠가 튜닝이 필요한 API라고 인계받았지만, 재 보니 2~3초라 우선순위를 미뤄 뒀습니다. 그러다 인프라팀에서 한 고객사에서 이 목록이 유독 느리다는 연락이 왔고, 현장에서 재 보니 약 7초였습니다.

원인

여러 API가 함께 쓰는 게시판 메인 쿼리였습니다. 여러 사람의 수정이 쌓이면서 필요 없는 조인과, 이미 조인한 데이터를 다시 읽는 서브쿼리가 남아 있었습니다.

해결

  • LEFT JOIN → INNER JOIN, 쿼리 분리: 게시판과 게시글은 항상 짝이 있는데 LEFT JOIN으로 묶여 있었습니다. 트리 정보가 없는 일부 게시판 유형만 LEFT JOIN을 남기고 나머지는 INNER JOIN 쿼리로 나눴습니다. 공통 SELECT 절은 MyBatis <sql>/<include>로 묶었습니다. 이 단계에서만 3초 넘게 줄었습니다.
  • 같은 사원 테이블을 두 번 읽던 서브쿼리를 조인 한 번으로 바꿨습니다.
  • 권한 확인이 필요 없는 관리자 목록은 동적 SQL로 권한 조인과 쓰지 않는 컬럼을 건너뛰게 했습니다.

결과

응답 시간이 약 7초에서 3초 미만으로 줄었습니다.

돌아보며

대용량 엑셀 업로드 OOM 해결 (POI → SAX)

엠케이원 · Java · Spring Boot · Apache POI · 2023

엑셀을 읽어 DB에 저장하는 마이그레이션 API가 5만 건을 넘기면 느려지고 OOM이 났습니다. 파일을 통째로 올리지 않고 행 단위로 읽는 방식으로 바꿔 15만 행을 13초에 처리하게 했습니다.

문제

처음에는 Apache POI의 XSSFWorkbook으로 구현했습니다. 코드는 간단했지만, 5만 건 정도부터 속도가 크게 떨어지고 OOM이 발생했습니다.

원인

XSSFWorkbook은 파일 전체를 메모리에 올리고, 셀 하나하나를 자바 객체로 만듭니다. 행이 늘수록 힙 사용량도 그대로 늘어납니다.

해결

  • XSSFReader와 SAX 파서(XSSFSheetXMLHandler)로 시트를 행 단위로 읽고, SheetContentsHandler를 구현해 처리했습니다.
  • 숫자가 지수 표기로 바뀌지 않도록 DataFormatter에 형식을 지정했습니다.
  • 템플릿 헤더 행, 필수값이 빈 행, 빈 시트를 걸러낸 뒤 헤더 기준으로 매핑했습니다.
  • 처리가 길어 요청이 묶이지 않도록 전용 스레드 풀(core 5, max 20, queue 50)에서 비동기로 처리하고, 응답은 먼저 돌려줬습니다.

결과

15만 행 기준 13초에 처리됩니다.

돌아보며

읽기는 스트리밍으로 바꿨지만 읽은 행은 아직 리스트에 모아 두고 있습니다. 파일이 더 커지면 일정 행 단위로 끊어 바로 저장하는 게 다음 개선입니다.
